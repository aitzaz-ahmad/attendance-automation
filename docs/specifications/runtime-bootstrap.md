## Purpose

This specification defines the canonical runtime bootstrap and seed-file
expectations for Attendance Automation v2.

It owns the required Pi4 bootstrap inputs, load order, generated-versus-required
file expectations, fail-fast behaviour, and recovery-bootstrap relationship to
the FSM and [Reliability Model](reliability-model.md).

## Scope

This specification covers:

- Pi4 bootstrap order;
- biometric device configuration file expectations;
- runtime snapshot file expectations;
- review period file expectations;
- generated versus required files;
- initial state expectations;
- missing-file behaviour;
- corrupt-file behaviour;
- fail-fast rules;
- recovery bootstrap;
- relationship to FSM and the [Reliability Model](reliability-model.md);
- v2 mandatory requirements; and
- v3/future bootstrap boundaries.

This specification does not cover:

- full implementation proposals;
- code-level refactoring plans;
- future advanced recovery tooling;
- biometric device configuration field definitions;
- messaging transport mechanics;
- backend response payload fields; or
- deployment provisioning steps.

## v2 Requirements

The Pi4 runtime bootstrap order for v2 is:

1. Configure runtime logging.
2. Create an empty in-memory Pi4 runtime state.
3. Load `biometric_device_config.json`.
4. Validate biometric device configuration according to
   [Biometric Device Configuration](biometric-device-configuration.md).
5. Derive runtime device identity from the configured `site_id`.
6. Construct the concrete biometric device through the device factory.
7. Construct the transformation strategy for the configured vendor.
8. Construct the messaging runtime for the configured site identity.
9. Load `review_period.json` and apply it to runtime state.
10. Load `snapshot.json` and apply checkpoint state to runtime state.
11. Compose and return the Pi4 workflow.
12. Start workflow execution.

Bootstrap must be deterministic. Given identical configuration, runtime files,
and inputs, bootstrap must construct an identical runtime graph. Bootstrap must
not introduce non-deterministic runtime composition.

`biometric_device_config.json` is a required bootstrap input. It is not
generated by the runtime. Missing, malformed, unsupported, or invalid biometric
device configuration is a deterministic startup failure and must fail fast.
The runtime must not silently fall back to another device, vendor, site, or
configuration source.

`review_period.json` is a required v2 seed and runtime persistence file for
review-period metadata. It must be present at bootstrap unless a later accepted
owner defines a generated initial-review-period path. It must contain a JSON
mapping compatible with the current review-period model and backend response
contract. A missing or corrupt review-period file must fail explicitly and must
not be hidden as an empty review-period business response.

`snapshot.json` is a required v2 runtime checkpoint file. It must be present at
bootstrap unless a later accepted owner defines a generated initial snapshot.
It must contain a JSON mapping compatible with the runtime checkpoint model.
Current checkpoint data includes:

- `pi4_state`;
- `sys_flags`;
- `sheet_id`; and
- `last_stored_timestamp`.

The snapshot is a recovery input, not a source of new architecture. Missing,
malformed, or corrupt snapshot data must fail explicitly unless a future
accepted owner defines a safe initialisation path.

Generated versus required file expectations are:

| File | v2 expectation |
| --- | --- |
| `biometric_device_config.json` | Required deployment input; not runtime-generated |
| `review_period.json` | Required seed/runtime file; updated after accepted review-period responses |
| `snapshot.json` | Required seed/recovery file; updated only through checkpoint persistence |

Initial state expectations are:

- bootstrap starts with an empty in-memory Pi4 runtime state;
- device identity is populated from validated biometric device configuration;
- review-period metadata is populated from `review_period.json`;
- checkpoint state is populated from `snapshot.json`;
- workflow execution starts only after required bootstrap inputs are loaded;
- bootstrap must not communicate with the biometric device before valid device
  configuration and device construction complete; and
- bootstrap must not treat missing local state as successful recovery.

Missing-file behaviour is fail-fast for all required v2 bootstrap files. A
missing file is an operational/provisioning failure unless an accepted owner
defines the file as generated for that path.

Corrupt-file behaviour is fail-fast for all required v2 bootstrap files.
Invalid JSON, missing required data, unparseable timestamps, unsupported
vendors, and invalid field types must surface explicitly instead of silently
falling back to defaults.

Recovery bootstrap must follow the [Reliability Model](reliability-model.md).
At restart, the runtime loads the last checkpointed non-waiting state from
`snapshot.json`. Waiting states must not be persisted as restart targets.
If the process stopped while waiting for a response, restart resumes from the
previous checkpointed non-waiting state and may repeat a request or backend
attempt. That repeated attempt is tolerated by the v2 reliability model.

The FSM relationship is:

- ADR-0004 owns the FSM, workflow, runtime, and execution-boundary rationale;
- the FSM owns waiting-state classification and checkpoint eligibility;
- workflow/runtime coordinates checkpoint timing;
- persistence owns snapshot serialisation and file I/O; and
- bootstrap loads persisted state but does not decide retry or recovery
  transitions.

## v3 / Future Boundary

The following concerns are outside v2 runtime bootstrap unless promoted by a
later accepted repository authority:

- advanced recovery tooling;
- generated first-run provisioning workflows;
- operator-guided repair tools for corrupt files;
- atomic snapshot redesign;
- persisted retry counters;
- correlation identifiers for request/response recovery;
- dynamic configuration services;
- centralised secrets management; and
- automatic reconstruction of missing local runtime files.

Undecided bootstrap implementation details are implementation-defined and
belong to future proposal or implementation work.

## Non-Goals

This specification does not:

- redesign the Pi4 runtime;
- define code-level refactoring tasks;
- create a new FSM design;
- define biometric device configuration fields;
- define backend response fields;
- define Pub/Sub routing or ACK policy;
- define retry budgets;
- define deployment steps; or
- update README files, diagrams, GitHub issues, or milestones.

## Validation

Changes to this specification must validate that:

- bootstrap order remains aligned with the accepted runtime composition
  boundary;
- required local files are documented without inventing fallback behaviour;
- missing and corrupt bootstrap data fail explicitly;
- recovery behaviour references the [Reliability Model](reliability-model.md)
  rather than duplicating it;
- local Markdown links resolve; and
- repository validation follows [Validation Gates](../workflows/validation-gates.md).
